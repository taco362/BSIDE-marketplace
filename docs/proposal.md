# B-SIDE — 프로젝트 요구사항 명세서

> 이 문서는 서비스 요구사항과 확정된 정책의 기준 문서다.
> 구현 방법(컨트랙트 구조, 상태 전이 세부 조건, 데이터 흐름)은 [architecture.md](architecture.md), 진행 상황은 [progress.md](progress.md)를 참고한다.
> 결정 사항은 8장에서 `D번호`로 관리하며, 본문의 "확정:" 표기는 해당 결정을 가리킨다.

## 1. 프로젝트 개요

B-SIDE는 독립 아티스트의 수익 환원과 거래 투명성 확보를 위한 NFT 기반 실물 굿즈 중고거래 플랫폼이다.

아티스트는 굿즈에 대응하는 NFT를 발행하고 재판매 정책을 설정할 수 있다. 이용자는 플랫폼에서 NFT와 연결된 실물 굿즈를 거래하며, 이전 거래 이력과 상품 상태 기록을 조회할 수 있다.

스마트 컨트랙트를 이용하여 거래 대금과 NFT를 에스크로로 관리하고, 거래 완료 시 재판매 정책에 따른 로열티 정산 및 NFT 소유권 이전을 수행한다.

### 핵심 목표

- 아티스트의 NFT 발행 및 재판매 정책 설정
- NFT 기반 소유권 이전 및 거래 이력 조회
- 상품 상태 정보와 사진의 무결성 검증
- 스마트 컨트랙트 기반 에스크로 거래
- 재판매 정책에 따른 거래 제한 및 자동 정산
- 중복 판매와 중복 정산 방지

## 3. 사용자 역할

공통:
- 별도의 회원가입, 아이디·비밀번호 로그인은 두지 않는다. 사용자는 지갑 주소로 식별한다.
- 누구나 지갑 연결 없이 상품 목록, 상세 정보, 거래 이력을 조회할 수 있다.
- 발행, 판매 등록, 구매, 수령 승인, 출금 등 트랜잭션이 필요한 기능에서만 MetaMask 연결을 요구한다.

### 아티스트

- 승인된 아티스트는 NFT를 발행할 수 있다.
- NFT 발행 시 최초 판매가와 재판매 정책을 지정한다.
- 발행 이후 재판매 정책은 변경할 수 없다.
- 창작자 상생형 거래에서 로열티를 지급받는다.
- 구매자로부터 선택적 후원금을 받을 수 있다. (Phase 3)

### 판매자

- 소유한 NFT와 연결된 실물 상품을 판매 등록한다.
- 상품 상태와 사진을 등록한다.
- NFT를 에스크로 컨트랙트에 예치한다.
- 거래 완료 시 정산 금액을 지급받는다.

### 구매자

- 판매 상품과 NFT 발행 정보를 조회한다.
- 과거 거래 및 상품 상태 이력을 조회한다.
- 거래 대금을 예치한다.
- 실물 수령 후 거래를 승인한다.
- 미수령 또는 상태 불일치 시 이의를 제기한다.

### 관리자

- 아티스트 등록(지갑 주소 + 활동명) 및 승인 권한을 관리한다.
- 분쟁 거래를 확인하고 사전에 정의된 규칙에 따라 처리한다.

## 4. 주요 기능 요구사항

### FR-01. 아티스트 등록 및 NFT 발행

- 승인된 아티스트만 NFT를 발행할 수 있다.
- NFT는 개별 실물 굿즈에 대응하는 고유 Token ID를 가진다.
- 발행 시 아티스트 주소, 최초 판매가, 재판매 정책을 기록한다.
- 재판매 정책은 발행 이후 변경할 수 없다.
- NFT 메타데이터는 IPFS에 저장할 수 있다.
- 최초 발행한 NFT를 구매자에게 판매하는 기능을 제공한다.

확정:
- 아티스트 승인: 관리자가 아티스트 지갑 주소와 활동명을 함께 등록하거나 승인을 회수한다. 활동명은 관리자가 다시 등록해 변경할 수 있다. 화면에는 승인된 아티스트의 활동명과 인증 표시를 보여주며, 승인이 회수되면 활동명은 남고 인증 표시만 제거된다. 아티스트의 신원 확인과 신청 접수는 플랫폼 밖에서 한다. (D7)
- 최초 판매 절차: 아티스트 지갑으로 발행한 뒤 재판매와 같은 에스크로 흐름으로 판매한다. 판매가는 발행 시 기록한 최초 판매가로 고정하며, 로열티는 계산하지 않는다. (D1)
- 최초 판매 자격: NFT가 아티스트 지갑을 한 번이라도 떠나면 최초 판매 자격이 종료된다. 플랫폼 밖 전송도 포함하며, 에스크로에 예치하는 경우는 제외한다. 자격 종료는 "플랫폼에서 최초 판매가 완료됨"과 같은 뜻이 아니며, 화면에서는 두 경우를 구분해 표시한다. (D9)
- NFT 발행 수수료: 받지 않는다. (D6)
- 발행 메타데이터 업로드: 아티스트가 발행 화면에서 굿즈 이름, 설명, 대표 이미지(1장, D11의 사진과 같은 형식·용량 제한)를 입력하면 서버가 IPFS에 업로드한 뒤 발행한다. 아티스트가 Pinata를 직접 사용할 필요가 없다. 업로드는 승인된 아티스트만 할 수 있다. (D13, D12)

### FR-02. 재판매 정책

NFT 발행 시 다음 세 가지 정책 중 하나를 선택한다.

**정가 보호형**
- 최초 판매가를 기준으로 재판매 가격 상한을 적용한다.
- 상한을 초과한 가격으로 판매 등록할 수 없다.

**창작자 상생형**
- 재판매 가격에 제한을 두지 않는다.
- 거래 완료 시 판매 금액의 일정 비율을 아티스트에게 로열티로 지급한다.

**자유 거래형**
- 재판매 가격 제한이 없다.
- 의무 로열티가 없다.

확정:
- 수치는 아티스트가 발행 시 허용 범위 안에서 지정한다. (D3)
  - 정가 보호형 상한: 최초 판매가의 100% ~ 150%
  - 창작자 상생형 로열티: 재판매 금액의 1% ~ 10%
- 최초 판매 이후 아티스트가 다시 판매하는 경우에도 일반 재판매와 동일한 정책을 적용한다. 이때 로열티 수령자가 판매자 본인이므로 로열티는 0으로 기록한다. (D10)

### FR-03. 상품 등록 및 상태 기록

- NFT 소유자는 해당 상품을 중고거래에 등록할 수 있다.
- 판매자는 개봉 여부, 사용 상태, 하자 정보 및 사진을 입력한다.
- 상세 정보와 사진은 오프체인(IPFS)에 저장한다.
- 상품 상태 기록의 콘텐츠 식별자(CID)를 온체인 거래 정보와 연결한다.
- 과거 거래 당시 등록된 상태 정보를 조회할 수 있다.

확정:
- IPFS 업로드 방식: Next.js 서버(Route Handler)를 거쳐 Pinata에 업로드한다. Pinata API 키는 클라이언트에 노출하지 않는다. (D8)
- CID 연결 시점: 판매 등록 시점에 거래 정보에 고정하고, 거래 완료 시 완료 기록에 같은 CID를 남긴다. 구매 후 판매자가 상태 정보를 바꿔치기하지 못하게 하기 위함이다.
- CID는 비워 둘 수 없다. 상태·사진 등록 기능이 구현되기 전(Phase 1)에는 Pinata에 수동으로 업로드한 실제 CID를 사용하며, 가짜·임시 CID로 NFT를 발행하지 않는다.
- 입력 항목과 사진 제한 (D11)
  - 필수: 개봉 여부(미개봉/개봉 중 선택), 사용 상태 설명, 사진 1장 이상
  - 선택: 하자 정보 (비우면 "없음"으로 기록)
  - 사진: 1~5장, 장당 4MB 이하, JPEG·PNG·WebP만 허용
  - 최초 판매(D1)는 위 항목을 입력하지 않는다. 아티스트가 막 발행한 상품이므로, 서버가 "아티스트 최초 판매" 상태 기록을 자동으로 작성하고 사진은 발행 메타데이터의 대표 이미지로 대신한다. 아티스트 재판매(D10)를 포함한 재판매는 위 항목을 입력한다. (2026-11-26 변경)
- 업로드 보호와 기록 작성 (D12)
  - 업로드 전에 지갑 메시지 서명(가스비 없음)으로 본인을 확인한다. 상태 기록은 해당 NFT의 현재 소유자만 업로드할 수 있다.
  - 상태 기록의 토큰 ID, 판매자 주소, 작성 시각, 사진 CID는 판매자가 아니라 서버가 채운다. 판매자는 상태 정보와 사진만 입력한다.
  - 한계: 화면을 거치지 않고 컨트랙트를 직접 호출해 임의의 CID로 판매 등록하는 경우는 막을 수 없다. 컨트랙트는 CID가 비어 있지 않은지만 확인한다.
- 같은 NFT가 여러 번 거래되면 거래마다 그 시점의 상태 기록이 남으며, 거래 이력에서 모두 조회할 수 있다.
- 상태 기록 모순 경고 (D14)
  - 판매 등록된 상태 기록이 같은 NFT의 이전 완료 거래 기록과 맞지 않으면 경고한다. 예: 이전 거래에서는 개봉이었는데 이번에는 미개봉, 이전 기록의 하자가 이번에는 "없음"
  - 판매 등록은 막지 않는다. 판매자에게는 판매 등록 화면에서 안내하고, 구매자에게는 거래 상세와 토큰 페이지에서 경고한다.
  - 경고는 AI가 아니라 정해진 규칙으로 판정하며, B-SIDE에 남은 기록끼리만 비교한다.
- AI 상태 기록 작성 보조 (D14): 판매자가 올린 사진으로 AI가 사용 상태·하자 설명 초안을 판매자 말투로 만들 수 있다. 초안은 판매자가 확인·수정해서 등록하며, AI 초안을 활용한 기록에는 그 사실을 표시한다(판매자 자기 신고).
  - 개봉 여부는 AI가 판단하지 않는다. 판매자가 직접 선택하며, 판매 등록 화면은 미리 선택된 값 없이 시작한다(선택하지 않으면 등록할 수 없음). (2026-11-28 사용자 결정)

### FR-04. 상품 검색 및 거래 이력 조회

- 판매 중인 상품 목록을 조회할 수 있다.
- 상품 상세 페이지에서 가격, 상태, 발행자, 재판매 정책을 확인할 수 있다.
- NFT별 플랫폼 내 거래 이력을 조회할 수 있다.
- 거래 당시 등록된 상태 정보와 소유권 이전 기록을 확인할 수 있다.

확정:
- DB 없이 조회한다. 현재 거래 상태는 스마트 컨트랙트의 상태값을, 거래 이력은 컨트랙트 이벤트 로그를 기준으로 한다. (D8)
- AI 거래 이력 요약 (D14): 토큰 페이지에서 요청하면 거래 횟수, 가격 변화, 상태 변화, 모순 경고를 AI가 문장으로 요약한다. 숫자는 시스템이 계산하고 AI는 문장만 작성하며, 참고용임을 표시한다.

### FR-05. 에스크로 거래

- 판매자는 NFT를 스마트 컨트랙트에 예치하고 판매를 등록한다.
- 구매자는 판매 가격에 해당하는 ETH를 예치한다.
- 구매가 확정되면 해당 상품의 중복 구매를 차단한다.
- 구매자가 실물 상품을 수령하고 승인하면 거래를 완료한다.
- 거래 완료 시 NFT를 구매자에게 이전하고 판매 대금을 정산한다.
- 창작자 상생형 거래에서는 로열티를 분배한다.

확정:
- 배송 확인 방식: 별도의 배송 상태를 두지 않는다. 구매자의 수령 승인 또는 기한 경과로 거래를 확정한다. (D2)
- 수령 승인 기한: 구매 대금 예치 후 일정 기한(`confirmPeriod`) 안에 구매자가 승인하지도 이의를 제기하지도 않으면 판매자가 정산을 청구할 수 있다. 기한 값은 배포 시 설정하며, 시연에서는 짧게 설정한다. (D2)
  - Sepolia 시연 배포 값: 300초(5분). 과제 시연용 값이다. (2026-11-27 결정)
  - 기한을 구매(대금 예치) 시점부터 계산하는 것은 MVP의 단순화된 설계다. 실제 서비스에서는 배송 기간을 고려해 충분히 긴 기한을 설정해야 한다.
- 플랫폼 수수료: MVP에서는 받지 않는다. 판매 대금은 판매자 몫과 로열티로만 나뉜다. (D6)
- 정산 금액은 컨트랙트에 적립되고, 수령자가 직접 출금한다.

### FR-06. 거래 취소 및 분쟁 처리

- 판매 등록 취소 기능을 제공한다.
- 구매 후 미배송, 미수령 또는 상태 불일치에 대해 이의를 제기할 수 있다.
- 분쟁이 발생한 거래는 자동 정산을 보류한다.
- 관리자 중재 결과에 따라 환불 또는 정산한다.
- 취소 시 NFT와 예치금은 정의된 조건에 따라 반환한다.

확정:
- 판매 등록 상태(LISTED): 판매자는 언제든 취소할 수 있으며, NFT는 판매자에게 반환된다. (D4)
- 구매 대금 예치 이후(LOCKED): 판매자가 스스로 전액 환불하는 경우에만 취소된다. NFT는 판매자에게 반환된다. (D4)
- 자동 취소 기한: 두지 않는다. 기한 경과 시에는 취소가 아니라 판매자 정산 청구가 가능해진다. (D2)
- 분쟁 제기: 구매자만 수령 승인 기한 안에 제기할 수 있다. (D5)
- 관리자 권한과 분쟁 해결 기준: 관리자는 다음 두 결과 중 하나만 선택할 수 있다. (D5)
  1. 구매자 전액 환불 + NFT 판매자 반환 → CANCELLED
  2. 판매자 정산 + NFT 구매자 이전 → COMPLETED
- 분쟁 사유 기록 (D15): 구매자는 분쟁을 제기할 때 사유를 고르고 설명·사진을 남긴다. 기록은 IPFS에 올라가 고칠 수 없으며, 관리자 중재 화면과 거래 상세에 표시된다. 관리자는 이 기록과 판매자의 상품 상태 기록을 근거로 판단한다.

### FR-07. 거래 상태 관리

거래 상태를 스마트 컨트랙트에서 관리한다.

기본 상태:
- LISTED: 판매 등록 및 NFT 예치 완료
- LOCKED: 구매 대금 예치 완료
- COMPLETED: 수령 승인 및 정산 완료

추가 상태:
- CANCELLED: 거래 취소
- DISPUTED: 분쟁 발생

- 상태 전이는 사전에 정의한 조건에 따라서만 허용한다. (전이 조건: [architecture.md](architecture.md) 4장)
- 거래 완료 후 동일 거래에 대한 중복 정산을 차단한다.

## 5. 주요 사용자 흐름

### 흐름 A. 최초 발행 및 판매

1. 아티스트가 지갑을 연결한다.
2. NFT 발행 정보를 입력한다.
3. 재판매 정책을 선택한다.
4. NFT를 발행한다.
5. 최초 판매 상품을 등록한다. (판매가 = 최초 판매가)
6. 구매자가 ETH를 예치한다.
7. 아티스트가 실물 상품을 배송한다.
8. 구매자가 수령 후 거래를 승인한다. (또는 기한 경과 후 아티스트가 정산 청구)
9. 거래 완료 후 NFT 소유권이 구매자에게 이전된다.

### 흐름 B. 중고 재판매

1. NFT 소유자가 지갑을 연결한다.
2. 판매할 NFT를 선택한다.
3. 상품 상태와 사진을 등록한다.
4. 판매 가격이 정책을 준수하는지 확인한다.
5. NFT를 에스크로에 예치하고 판매를 등록한다.
6. 구매자가 ETH를 예치한다.
7. 판매자가 실물 상품을 배송한다.
8. 구매자가 수령 후 거래를 승인한다. (또는 기한 경과 후 판매자가 정산 청구)
9. 스마트 컨트랙트가 정산 및 NFT 이전을 수행한다.
10. 거래 이력과 상태 기록을 조회할 수 있도록 반영한다.

### Phase 1 — 핵심 거래 MVP

- 지갑 연결
- NFT 발행
- 재판매 정책 등록 및 검증
- NFT 판매 등록

- 스마트 컨트랙트 단위 테스트

### Phase 2 — 상품 정보 및 거래 안정성

- 거래 취소 및 환불

### 향후 개선 사항 (범위 미정)

- 배송 완료 시점 기반 수령 승인 기한: 현재는 구매 시점부터 `confirmPeriod`를 계산한다(D2). 배송 완료 시점부터 기한을 계산하는 방식을 검토한다. 거래 상태 머신 변경이 필요하므로 MVP에서는 다루지 않는다.

## 7. 시스템 제약 및 보안 요구사항

- 재판매 정책은 NFT 발행 이후 변경할 수 없다.
- 승인되지 않은 사용자는 NFT를 발행할 수 없다.
- NFT 소유자가 아닌 사용자는 해당 NFT를 판매할 수 없다.
- 동일 NFT를 여러 활성 거래에 동시에 등록할 수 없다.
- 동일 거래를 중복 정산할 수 없다.
- 거래 취소와 환불은 정의된 상태 및 권한 조건에 따라 수행한다.
- 스마트 컨트랙트는 재진입 공격 및 무단 호출에 대비해야 한다.
- 개인키 및 API 비밀값을 소스코드나 Git 저장소에 저장하지 않는다.
- 외부 거래에 대해서는 로열티 지급이나 거래 이력 기록을 강제하지 않는다.
- NFT는 실물 상품의 정품 여부나 실제 상태를 보장하지 않는다.

알려진 한계 (상세: [architecture.md](architecture.md) 8장):
- 플랫폼 밖 NFT 전송이나 오프체인 추가 금액 거래로 가격 상한과 로열티를 우회하는 것은 막을 수 없다.
- 관리자는 단일 지갑이며, 분쟁 중재는 관리자 신뢰에 기반한다. 관리자가 처리하지 않은 분쟁은 계속 보류된다.

## 8. 결정 사항

### 확정된 결정

| 번호 | 항목 | 결정 |
|---|---|---|
| D1 | 최초 NFT 판매 방식 | 아티스트 지갑으로 발행 후 재판매와 같은 에스크로 흐름으로 판매. 판매가는 최초 판매가로 고정, 로열티 없음 |
| D2 | 배송 및 수령 확인 | 별도 배송 상태 없음. 구매 후 `confirmPeriod` 안에 승인·이의가 없으면 판매자가 정산 청구 가능. 기한 값은 배포 시 설정 (Sepolia 시연 300초) |
| D3 | 정가 보호형 상한 / 로열티 비율 | 아티스트가 발행 시 지정. 상한 100~150%, 로열티 1~10% |
| D4 | 거래 취소와 환불 조건 | LISTED: 판매자 언제든 취소. LOCKED: 판매자 자발적 전액 환불만 가능 |
| D5 | 분쟁 처리 권한과 절차 | 구매자만 기한 내 제기. 관리자는 "구매자 환불" 또는 "판매자 정산" 중 택1 |
| D6 | 수수료 | MVP에서는 플랫폼 수수료와 발행 수수료 없음 |
| D7 | 아티스트 승인 방식 | 관리자가 지갑 주소와 활동명을 함께 등록(활동명 변경 가능)·회수. 승인된 아티스트는 활동명 + 인증 표시, 회수 시 인증 표시만 제거 |
| D8 | 데이터 저장 및 DB 범위 | DB 없음. 핵심 정보는 컨트랙트, 상세 정보·사진은 Pinata IPFS(CID를 온체인 연결). 현재 상태는 컨트랙트 상태값, 이력은 이벤트 로그 기준. 조회 로직은 PostgreSQL로 교체할 수 있도록 분리 |
| D9 | 최초 판매 자격 | NFT가 아티스트 지갑을 한 번이라도 떠나면(에스크로 예치 제외) 최초 판매 자격 종료. 플랫폼 최초 판매 완료와는 구분해 표시 |
| D10 | 아티스트의 재판매 | 일반 재판매와 동일한 정책 적용. 로열티는 0으로 기록 |
| D11 | 상품 상태 기록 항목과 사진 제한 | 개봉 여부·사용 상태 설명·사진 1장 이상 필수, 하자 정보 선택. 사진 1~5장, 장당 4MB, JPEG·PNG·WebP. 최초 판매는 입력 없이 서버가 자동 기록(사진 = 발행 대표 이미지) |
| D12 | 업로드 보호와 기록 작성 | 업로드 전 지갑 메시지 서명으로 본인 확인(상태 기록: NFT 현재 소유자, 발행 메타데이터: 승인된 아티스트). 토큰 ID·판매자 주소·작성 시각·사진 CID는 서버가 채움 |
| D13 | 발행 메타데이터 업로드 | 발행 화면에서 이름·설명·대표 이미지를 입력하면 서버가 업로드 후 발행 (Phase 2 범위에 추가) |
| D14 | AI 보조 기능 | ① 상태 기록 모순 경고: 규칙으로 판정, 등록은 허용, 판매자 안내 + 구매자 경고(거래 상세·토큰 페이지) ② AI 상태 초안: 사용 상태·하자만 판매자 말투로 작성(개봉 여부는 판매자가 직접 선택, 기본 선택 없음), 판매자가 확인·수정 후 등록, 기록에 AI 초안 활용 표시(자기 신고) ③ AI 이력 요약: 숫자는 시스템 계산, 참고용 표시. AI 결과는 컨트랙트 판정·정산에 쓰지 않음 (2026-11-27 추가) |
| D15 | 분쟁 사유 기록 | 사유 5개 중 택1(상품 미수령, 상태 기록과 다름, 배송 중 파손, 가품 의심, 기타). 설명은 "기타"일 때만 필수(최대 500자), 사진 선택 최대 3장(D11과 같은 형식·크기). 제기 전 지갑 서명으로 구매자 확인, 서버가 기록 작성·IPFS 업로드. 컨트랙트는 변경하지 않으며, 거래와 기록의 연결은 Pinata 파일 꼬리표로 찾는다 (2026-11-28 추가) |

온체인 상태 기록의 구체적인 데이터 구조는 [architecture.md](architecture.md)에서 정의한다.
